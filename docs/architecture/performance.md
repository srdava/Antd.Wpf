# 性能契约与回归方法

状态：预算仍待完整硬件校准。M0已运行PF02/PF05的布局/Dispatcher代理采样，结果与限制见[实施状态](../implementation-status.md)；其余场景未测。与[架构设计](README.md)一起作为组件验收条件，代理采样不等于完整发布门槛通过。

## 1. 首要性能风险和实现约束

| 热路径 | 必须采用的策略 | 必须发现的失败模式 |
| --- | --- | --- |
| Measure/Arrange | 只测量真实孩子/视口；布局失效局部化，颜色变化只重绘 | 滚动或Hover触发全树重新测量、递归LayoutUpdated/UpdateLayout |
| 列表生成 | 有限视口、回收容器、状态按Key还原 | 加入1万项就创建1万个视觉项、回收后选中/错误串行 |
| Table | 行/列虚拟化分别检查；过滤排序与显示分离 | 套外部ScrollViewer、复杂模板导致全部列或行展开 |
| Tree | 普通树小规模验收；大型树用可见节点投影 | 每次展开/搜索遍历所有节点并创建完整视觉树 |
| 输入搜索 | IME提交后处理；宿主取消与版本防旧；必要时合并连续请求 | 每按键同步全量排序/网络、旧请求覆盖新结果、UI线程阻塞 |
| 主题 | 有效作用域缓存，token只在设置变化时派生 | 每个控件各自产生一整套Brush、切换主题重建控件 |
| 动画 | RenderTransform/Opacity，离屏暂停，关闭动画路径 | 每帧变更尺寸触发布局、无效全局Rendering订阅 |
| 图像 | 匹配显示尺寸解码、有界缓存、取消旧解码 | 原图全尺寸解码、无限静态缓存、源流长期占用文件 |
| 消息/弹层 | 每窗口有界队列、同Key更新、关闭路径幂等 | 消息风暴导致无限窗口/计时器、Owner关闭仍活跃 |

普通设置路径可以使用LINQ/易读代码；仅在测得的热点减少重复枚举、分配、装箱、反射与转换器层数。不能为了net8的Span/FrozenDictionary/GeneratedRegex在共享net48路径中盲目引入垫片或依赖。

## 2. 算法复杂度和视觉数量

- 普通堆叠/栅格布局目标O(n)，不能把查找上一列/兄弟位置的线性扫描嵌入每个孩子的布局循环。
- 单选/勾选状态查询目标均摊O(1) Key查找；祖先状态更新与变更路径相关。只有需要全树操作时才遍历全树。
- 平面表本地筛选O(n)，排序O(n log n)；不在每个单元格绑定中再次排序、分组或创建全量快照。
- 一次刷新只构建必要的数据视图。多列筛选批量更新后只刷新一次；数据源替换与普通属性更新分别测试。
- 首批固定高度虚拟列表的已实现行数目标为“可见行数 + 上下各不超过2个视口缓存”，不以源总量决定容器数。可变高度场景另记录测量缓存和定位复杂度。
- DataGrid的可见冻结列可增加容器数，测量时需记录；“有1万行”不能只检查第一个屏幕是否流畅。
- Masonry、合并单元格、分组粘性头与嵌套表不套用普通列表预算，必须提供自己的场景和开关组合矩阵。

## 3. UI线程和并发

1. UI线程不执行同步文件/网络I/O或阻塞等待Task；事件处理最终观察异常。纯计算使用脱离DispatcherObject的数据快照，只有必要的结果合并回Dispatcher。
2. 长计算不是每个按键都Task.Run；先合并输入、取消旧工作并确认需要异步，避免线程池/Dispatcher队列积压。
3. 高频进度/加载结果以批次呈现，常规通知不超过屏幕更新所需频率；Upload等建议最多10次/秒的可视进度更新。
4. 对可取消任务记录RequestVersion；取消是资源回收机制，版本校验是正确性机制。宿主忽略取消时仍不能接受旧结果。
5. UI线程上的ConfigureAwait(false)不能无差别添加；只有不访问UI的内部纯异步层才按上下文需求决定。
6. 子控件的瞬时状态不通过全局总线广播；Dispatcher操作应可合并/取消，卸载后完成的回调检查所属加载代次与Owner状态。

## 4. 首批资源上限

以下是内部默认预算，M0根据机器测量确认，默认不全部暴露为公共配置选项。

| 资源 | 初始预算/行为 | 超限处理 |
| --- | --- | --- |
| Message/Notification | 单窗口分别最多3条可见、20条等待；同Key就地更新 | 重复合并；超限释放最旧非关键提示并发出可观察状态，业务关键错误由持久界面呈现 |
| 图像解码缓存 | 窗口拥有的缓存最多64 MiB估算解码数据，单图先按显示尺寸解码 | LRU淘汰；被活动控件引用的图像仍计入活动内存；不声称缓存上限限制进程总内存 |
| 图像并发 | 每宿主最多2个解码/加载工作，滚动离屏可取消 | 仅保留仍需要的队列项；不得无限待处理 |
| 上传宿主示例 | 同时最多3个上传、100个等待；每文件可视进度最多10次/秒 | 超限停止接纳并明确报告；传输由宿主执行，控件不隐式启动网络 |
| 目录导入 | 最大深度32、枚举最多10,000项；默认跳过reparse point/符号链接 | 取消/超限/无权限返回部分结果和原因；RelativePath须落在选定根内 |
| 主题快照 | 纯数据缓存最多16个有效设置组合 | 淘汰旧组合；存活作用域自行持有当前快照 |
| 自动播放/计时 | 按可见任务调度，卸载或Owner销毁立即移除 | 不为不可见条目保留轮询 |

库接受外部ImageSource时缓存规则不能替外部所有者释放资源。图片大小、URI源、路径失败属于输入边界；压缩文件小不代表解码内存小，解码尺寸限制必须在分配前生效。

消息等待期间不消耗Duration，进入可见态后才计时；同Key更新复用活跃句柄，淘汰等待项也以Evicted完成Closed Task。显示Timer隐藏时暂停刷新，隐藏期间到期在恢复首帧计算补发一次Finished；Owner销毁不触发业务完成。时间敏感的业务调度由宿主拥有。

## 5. 参考硬件与采样协议

M0先记录真实设备，建议基线为Windows 11 x64、4核以上CPU、16GB内存、SSD、1920×1080、60Hz、100%缩放，另在150%/200%验证。net48与net8分别记录GC/运行时版本、渲染层级、显卡驱动、SDK、提交或源码快照hash。

- Release、无调试器、默认模板、相同数据seed；关闭与场景无关的后台负载。软件渲染/远程桌面/客户自定义模板结果单列。
- 冷启动至少10个独立进程；稳态操作预热5次后采样30次，报告p50/p95/max及样本数量。记录进程启动到Loaded与首帧/首次可交互的不同时间点。
- 各种时间段定义在场景驱动内：例如点击展开→下拉显示且可接收键盘；主题请求→主题字典提交并完成下一帧；不只计时一个设置属性的调用。
- UI帧间隔与Dispatcher延迟分开测量。CompositionTarget.Rendering回调间隔可作代理指标，但不是GPU呈现延迟证明；需要时用ETW/WPF事件交叉验证。
- 分配/堆保留通过适用运行时工具采集；计时采样与重型Profiler采样分开。统一场景，不强行用两个运行时不可比的计数API作同一指标。

## 6. 场景预算与准入门槛

预算在M0校准后冻结，任何修改要解释用户体验变化和原始数据。绝对预算与相对回归均要检查，不能因为基线已经慢就只看百分比。

| ID | 默认场景 | 初始绝对预算 | 必查证据 |
| --- | --- | --- | --- |
| PF01 | 空宿主与带200个常见控件页的冷启动差值 | 库引入的首个可交互时间p95增量≤300ms | 进程起止、加载组件数、程序集/资源加载 |
| PF02 | 200控件页Light/Dark切换 | p95≤200ms | 输入值/选区保留、资源字典数不持续增长 |
| PF03 | 1万行×10列DataGrid平面表初屏 | p95≤1s | 数据已准备；容器数、UI/渲染耗时分别记录 |
| PF04 | PF03连续滚动30秒 | 帧间隔代理p95≤33ms，常规输入延迟p95≤100ms | 行列虚拟化开启、分配速率、拖动与滚轮分别测 |
| PF05 | 1万项固定高度Select首次展开 | p95≤300ms | 生成项数与总数不线性相关，选中定位正确 |
| PF06 | 1万项本地简单文本过滤 | IME提交到可操作结果p95≤150ms | 扣除人为防抖时长并另列总延迟，旧结果不得覆盖 |
| PF07 | 十万节点源、约1千节点展开的大型树投影 | 首屏p95≤1s，局部展开p95≤150ms | 仅适用后续扁平虚拟树，不代表原生TreeView首批能力 |
| PF08 | Modal/Drawer打开与关闭 | 关闭动画时响应p95≤100ms | 焦点移动/恢复、重复确认、Owner关闭、Popup协调 |
| PF09 | 连续100次页面/弹层开关 | 不遗留已关闭Owner/控件/Timer强引用 | 任务结束、Dispatcher排空后WeakReference/堆根调查；GC仅用于验证宿主 |
| PF10 | 消息风暴/图像快速滚动 | 遵守队列/缓存/并发上限 | 正常错误可见、取消有效、无静态Owner引用 |

当可比条件下p95耗时或分配量比已批准基线恶化>10%，且超过测量噪声，应阻止性能敏感改动合入并调查。先用同一构建重跑至少两轮确认；共享CI性能不稳定时不能盲目失败，也不能忽略绝对预算失败。

## 7. 最小性能结果格式

每个结果应包含场景ID、提交/源码hash、目标TFM、宿主版本、OS/CPU/GPU/DPI、数据量/seed、模板及功能开关、工具版本、采样数、p50/p95/max、容器数、分配与GC、基线差值和原始采样路径。

测试输出归 `artifacts/performance/<revision>/<tfm>/<scenario>/`，保留原始CSV/JSON与必要trace，文档只摘要结果。跨框架结果先分别判预算，再解释差异；不得用net8的通过替代net48。

BenchmarkDotNet仅用于可独立运行的纯算法比较，不用来测量STA WPF窗口和用户交互。WPF UI场景通过Gallery/独立场景宿主驱动，热路径经trace定位后再写微基准。

## 8. dotnet skills 的使用时机

- `analyzing-dotnet-performance`：已有C#实现且明确热点后扫描，保留命中数/范围/平台限制，不能把模板外观直接当成性能结论。
- `dotnet-trace-collect`：出现真实CPU、GC、泄漏或阻塞问题时选择采集方式；Windows Framework优先PerfView/ETW，现代.NET可按权限使用PerfView或dotnet-trace。
- `microbenchmarking`：BenchmarkDotNet相关工作时使用；不以微基准代替UI场景。
- 构建慢时先使用`build-perf-baseline`，依据证据再进入MSBuild性能技能；构建耗时与用户UI耗时分开报告。
